TreeListItem — one row of a TreeList: a leaf, or a branch with the rows under it. It claims no role, and that is the decision this component had to make. TreeList claims `role="tree"` only when it is named, so a row cannot know which kind of list it is in — a `role="treeitem"` written here would be right in a named tree and a lie in every other one. It would be a lie in the named one too: a treeitem owes a reader aria-expanded, one tab stop for the whole widget and arrow-key movement between rows, and none of that exists without script. So this stays an `li` in a nested `ul`, which every browser and screen reader already reads correctly, and a tree somebody has genuinely wired up gets its roles from whatever wired it. Two shapes, decided by whether the slot holds anything — the split SideNavItem makes for the same reason. Empty, the row is a link, or a `span` when there is nowhere to go. Filled, the slot is the branch: the row becomes the `summary` of a native `details` and the rows under it a nested list, so a branch opens with no script, survives find-in-page and prints open. The chevron is decoration. The `summary` is already the control, already toggles on Enter and Space and already announces whether it is open; a button inside it would be a second control for one job, and one whose clicks the summary takes. So it is `aria-hidden`, and the stylesheet turns it from `details[open]` rather than from an `aria-expanded` the server would have to keep in step by hand. The guide — the hairline tying a branch to its rows — is an `li`, which is the only thing a `ul` may contain. It is out of flow and `aria-hidden`, so it neither takes space nor lands in the accessibility tree, and the list is still announced with the number of rows it really has. Selection is stated twice: `data-selected` for the tint, `aria-current` for the announcement, because the tint says "you are here" only to someone who can see it. {ariaCurrent}{f:if(condition: '{selected} == \'selected\'', then: 'page')}
